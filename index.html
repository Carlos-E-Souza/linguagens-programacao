Trabalho final · Linguagens de Programação · UnB

Chat em tempo real com Go e WebSockets

Sistema de mensagens instantâneas com conversas individuais (1:1) e em grupo. Um servidor concorrente em Go e um cliente desktop em Wails, feitos para explorar na prática o que a linguagem tem de mais característico: goroutines, channels e o runtime de concorrência.

O desafio: entregar muitas mensagens com baixa latência e pouco consumo de memória e CPU, sem perder nem embaralhar mensagens quando a conexão cai.

Dentro do servidor

Hub

Goroutine única dona do estado de roteamento. Valida, deduplica, atribui a sequence e entrega.

Clientes

Cada conexão tem uma goroutine de leitura e uma de escrita, com canal de envio com buffer.

Store pool

Workers gravam mensagens em lote no SQLite, com retry e backpressure, fora do caminho da entrega.

Funcionamento#

O caminho de uma mensagem, do login até a confirmação de leitura.

  1. Login. App.Login chama POST /api/auth/login; o servidor confere o bcrypt e devolve um JWT, salvo no cache local.
  2. Conexão. O cliente abre /ws com Authorization: Bearer; o Hub registra a conexão com suas goroutines.
  3. Presença. Na primeira conexão do usuário, os contatos recebem presence {online: true}.
  4. Envio. App.SendMessage gera um client_id (UUID), salva como pending e envia message.send.
  5. Roteamento. O Hub valida membro e tamanho, deduplica por (sender_id, client_id), atribui a sequence e entrega message.new aos membros online.
  6. Confirmação. A mensagem vai para a fila de persistência e o remetente recebe message.ack.
  7. Status. Destinatários enviam message.delivered e message.read; o Hub propaga message.status.
  8. Reconexão. Após uma queda, o cliente envia sync com a última sequence de cada conversa e recebe o que faltou, até sync.end.
  9. Saída. Fechamento do socket ou falha no heartbeat remove o usuário do Hub e avisa os contatos com presence {online: false}.

Recursos de Go#

O objetivo da disciplina: usar os recursos característicos da linguagem num caso real.

Goroutines

Duas por cliente conectado. Poucos kilobytes de pilha, escalonadas pelo runtime.

Channels

Comunicação entre goroutines. Buffers absorvem picos e isolam clientes lentos.

select

O laço do Hub trata registro, saída e mensagens sem bloquear.

sync.RWMutex

Protege o que a API lê do Hub (ex.: IsOnline) com leituras simultâneas.

Worker pool

Goroutines fixas consomem a fila de gravação no banco.

context.Context

Cancelamento e timeouts entre requisições, conexões e workers.

time.Ticker

Heartbeat com pings periódicos detecta conexões mortas.

Graceful shutdown

WaitGroup e sinais do SO: pendentes são gravadas antes de encerrar.

net/http

Servidor HTTP concorrente da biblioteca padrão, sem frameworks.

// laço central do Hub (ilustrativo)
for {
    select {
    case c := <-h.register:   h.add(c)
    case c := <-h.unregister: h.remove(c)
    case m := <-h.incoming:   h.route(m)
    case <-ctx.Done():        return
    }
}

Confiabilidade#

O TCP já trata perda, retransmissão e ordem no transporte. O projeto complementa isso na camada de aplicação:

MecanismoGarante
client_id (UUID do cliente)Reenvio sem duplicatas no servidor
message.ackMensagem sem ACK fica na fila e é reenviada após reconectar
sequence por conversaOrdem de exibição; atribuída pelo Hub, sem condição de corrida
sync / sync.endRecuperação do que chegou enquanto o cliente estava offline
Heartbeat (PING_INTERVAL, PONG_TIMEOUT)Conexões mortas são detectadas e liberadas
Backoff com jitter (1s → 30s)Reconexão automática sem sobrecarregar o servidor

Status de uma mensagem no cliente:

pending → sent (ACK) → delivered → read
        ↘ failed (erro definitivo do servidor)

Protocolo WebSocket#

Todo frame usa o mesmo envelope; o tipo define o formato de data.

{ "type": "message.send", "data": { "client_id": "…", "conversation_id": 1, "body": "Olá!" } }

Cliente → servidor

TipoCamposUso
message.sendclient_id, conversation_id, bodyEnvia uma mensagem
message.deliveredconversation_id, up_to_sequenceConfirma recebimento
message.readconversation_id, up_to_sequenceMarca como lidas
syncconversations: [{conversation_id, last_sequence}]Pede o que chegou offline

Servidor → cliente

TipoUso
message.ackMensagem aceita (client_id, id, sequence, created_at)
message.newNova mensagem numa conversa do usuário
message.statusUm membro confirmou entrega ou leitura
presenceUm contato entrou ou saiu
conversation.updatedConversa alterada (ex.: membros)
sync.endFim das mensagens pedidas em sync
errorErro ao tratar um frame
server.shutdownServidor encerrando

Como rodar#

Pré-requisitos: Go 1.26+, Node/npm, Wails CLI v2 e, no Linux, WebKitGTK 4.1.

# Terminal 1 — servidor em :8080
make server

# Terminal 2 — cliente desktop com hot reload
make dev

# Só a interface, com dados falsos (sem servidor)
make dev-mock

Testes e qualidade

make test      # testes dos dois módulos com -race
make vet       # análise estática
make e2e       # ponta a ponta (servidor em E2E_SERVER_URL)
make loadgen   # teste de carga: CLIENTS=100 MESSAGES=20

Fora do modo dev, o servidor exige JWT_SECRET. Copie back-end/.env.example para .env e ajuste os valores.
